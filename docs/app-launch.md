# 控屏应用启动

## 已修复的行为

原来的 `launch` 在调用 `startActivity()` 后立即返回，既没有确认目标前台，也没有区分系统确认弹窗、后台启动拦截或应用自行跳转。小米安全中心的 `com.miui.wakepath.ui.ConfirmStartActivity` 会显示“本次允许／始终允许／拒绝”；后台弹出界面权限并不能保证没有这项跨应用启动确认。

0.3.3 将控屏内的启动集中在模块无障碍执行器。需要后续识屏/点击/输入的任务先进入控屏会话，再使用 `launch`；提示模型不在会话外另调小爱原生 `app start`。普通仅打开应用的原功能保持原路由，这个提示不保证任意模型都正确选工具。

首次观察提供本机可见的可启动应用列表，模型使用包名。解析只接受启用且可导出的 MAIN/LAUNCHER 入口，不接收任意 Intent 或组件。一个包的多个 launcher 不再误判为名称歧义；不同包同名时要求包名。以模块身份提交标准 launcher Intent，保留既有任务；目标已在前台时不重复提交启动。

## 自动处理小米启动确认

按用户要求，这类打开应用确认自动处理，无需人工逐次点击。执行器仅在当前 `launch` 等待期间工作，核对：

- 窗口所属包为 `com.miui.securitycenter`；
- 固定资源 `permission_group_title` 为“启动应用”，`event_title` 的完整请求文案与模块发起方和本步目标包名/应用名称一致；
- 存在唯一、可见、启用且可点击的“本次允许”按钮，并有拒绝/取消选项。

每个动作最多点击一次“本次允许”，不选择“始终允许”，不修改系统授权数据库或全局策略。匹配的遗留同目标确认也可直接完成，不再提交第二次启动。其他应用伪造的文字、不同发起方/目标、相机/通讯录/安装等权限不会匹配。ROM 修改控件 ID、语言或文案后可能需要重新适配。

## 真实结果确认

启动后每 250 毫秒检查焦点窗口，要求目标包稳定前台至少 500 毫秒，整体最多等待 10 秒。自动点过允许也不等于启动成功；未真正打开、短暂闪现后退出或跳到其他应用，都不能报告已打开，不循环重试。任务取消和锁屏立即停止。

2026-10-18 工作树调整：出现可读的系统应用选择器、未匹配的启动确认或其他系统授权时，`launch` 返回待选择/确认的观察，同一任务继续，由模型规划下一步；这不等于目标已经进入前台。没有可处理的系统提示且仍无法确认目标时，保留启动超时暂停。匹配当前发起方和目标的“本次允许”仍最多自动点击一次。

后台 helper 的正式启动等待也接受本显示上的已知系统授权/应用选择窗口，以 `awaiting_confirmation` 回复，由模块返回新观察；不会因目标暂未占焦点而提前报启动失败。启动前后均检查目标应用的跨屏可见任务，发现主屏或其他屏的目标任务仍拒绝/停止；不在物理屏处理该确认。能力探针继续只把真实目标进入后台屏记为启动能力通过，待确认不是探针成功。

安全中心也有普通首页、清理和电池页面，不能仅凭其包名判定为授权。其可见 `permission_group_title` 将页面区分为启动/打开应用、其他授权和普通页面。普通页面和应用选择由模型操作，其他授权进入本会话 Manual / Auto / YOLO 的审批流程；安装、设备管理、无障碍、未知来源和关闭保护等严重授权保留人工确认。后台屏同样可读取和处理这些窗口，不再仅凭安全中心包名终止，也不会切到物理屏处理。

批准只绑定本步观察中的授权窗口。真正派发手势/输入前再次读取同一屏的前台与树；审批期间出现新授权或文案变化时，作废本步执行并返回新观察重新规划与审批。应用选择器不因此获得敏感系统权限的通行证；密码、安全窗口、锁屏等既有边界保留。后台树优先读取该显示上的焦点窗口，避免将底层目标应用的树当作当前弹窗。

系统弹窗分类仍受 ROM 模板和可读无障碍树限制：小米授权分类使用 `permission_group_title`，其他授权使用已知系统包；未知模板还会按“允许／同意／授权”等目标标签触发审批，未被识别的模板仍需模型正确标注敏感动作。未知模板和语言尚无新增实机验收，不应从历史启动确认测试推断全覆盖。

原生逐步会话的启动、主页、返回、等待不在执行前重复截图；这些动作不依赖旧坐标，执行后仍会截图。独立外部循环保留执行前观察与批准复核。坐标动作和输入仍保留执行前重观察校验。这样也避免快速连续工具调用触发系统的截图间隔错误。

物理屏截图在每次请求前保留至少 350 毫秒的单调时钟间隔，等待可取消且不复用旧图。截图 Frame 分别携带原始屏幕尺寸和实际压缩 JPEG 尺寸，`image_pixels` 按压缩图坐标换算，避免高分辨率手机点击偏移。

此外，`onInterrupt()` 的无障碍反馈中断不再被当作掉权限；旧服务实例退出也不会取消新实例的任务。真正的解绑/连接失效仍停止执行。

## 验证

```sh
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest :app:lintDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
python3 scripts/device_test.py --hook --launch
```

测试 APK 提供独立 launcher 测试页面；主机先通过安全中心导出的 MAIN/DEFAULT 入口打开普通页面（测试 ROM 的 launcher 入口已停用），探针从小爱实际 Hook 开始控屏，再按包名打开另一个 APK、检查真实前台和页面文本，最后按名称打开并确认原实例未重建。输出包含自动启动确认点击数。系统已信任该启动时计数可为 0；只有计数大于 0 且成功返回，才证明本次走过自动确认分支。最新结果见 [验证状态](validation.md)。

探针还通过自有页面打开真实 Android chooser，读取其 JPEG／树中的两个自有候选，验证 `awaiting_selection` 延续原会话，并按当前观察点击候选进入目标。2026-10-18 在最终 Debug APK 实机通过；该 ROM 的 chooser 仅暴露 `com.android.intentresolver` 根包名、没有可读标题，分类已覆盖这一形态。所有动作由确定性测试发起，没有调用真实模型，也不证明未知小米授权模板可全部处理。

测试页面不作为日常应用启动的中转。launcher fixture 不保留历史且不进入最近任务；主机脚本结束时发送仅 shell/DUMP 可用的清理广播，移除仍在前台的 fixture。Runner 结束时同时移除模块自己的后台 FixtureActivity，避免下一次小爱收起时露出上轮测试页面。
