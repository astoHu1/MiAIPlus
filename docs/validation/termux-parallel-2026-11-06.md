# 内置 Termux 并行调用与失败恢复（2026-11-06）

用同签名的优化 Preview 覆盖安装，LSPosed 在原小爱进程中自动热重载。设备为 HyperOS / Android API 37、小爱 8.3.30.4420；沿用已配置的真实模型和已运行的内置 Termux 服务。从小爱全屏对话发送测试提示，由模型选择并调用实际工具，没有使用 mock 或代理探针来替代小爱。

| 检查 | 实测 |
| --- | --- |
| 六条独立命令 | 小爱发出六次 `miaiplus_termux_run_digest`，六个探针各执行一次。设备记录显示，四个探针在起始后 4 毫秒内启动，约 3.1 秒内完成；剩余两个约在 3.38 秒启动、6.43 秒内完成。模型确认 6/6，设备文件独立核对执行身份为普通 Termux UID。 |
| 命令非零退出后继续 | 第一次 `run_digest` 返回 `ok:false`、退出码 7 和实际 stderr 探针文本。小爱在同一轮另发一次调用，读出提示中未给出的随机备选值，最终回复三项均正确。设备计数文件证明失败命令与后备命令各执行一次。 |

本地通过 538 项 JVM／Robolectric 测试、Debug／Release 完整 Lint（零错误），以及 Debug／Release／Preview／Debug AndroidTest APK 构建。回归覆盖并行上限、排队取消、第三方 MCP 与 Termux 分开执行、已知未执行的准入反馈，以及通过实际 loopback HTTP 接收非零退出诊断而不重发。

本轮未验证并行冷启动、小米官方模型或持久交互终端。队列上限与排队取消由本地测试验证；实机测的是模型发出六条调用的情形。已移除测试文件和临时界面探针，保留新版和原有模型、插件配置。
