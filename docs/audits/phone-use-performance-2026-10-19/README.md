## 给接手 Agent 的结论

**Phone Use 有值得验证的提效空间，优先看每步等待、主线程截图与树遍历、后台帧复制和请求图片负载。** 上轮适合一般后端的小优化（例如无工具 Responses 输出不序列化）未必对每轮有工具调用的 Phone Use 有明显收益。

建议先用下表挑一个切口，不一次实施全部候选。排序兼顾证据、范围与稳定性，不是实测收益排行榜。

| 顺序 | 候选 | 为什么值得先看 | 最小边界 |
| --- | --- | --- | --- |
| 1 | P01 无配置 IPC 延迟创建 Config | `poll` 和 `screen_state` 持续执行，却无须完整配置派生；改动范围小 | 分支局部新鲜快照，不加跨请求缓存 |
| 2 | P02/P03 省掉策略确定不用的树 dump；相同树解析一次 | 普通物理 tap/type 的执行阶段三次 dump 有机会降为一次；命中相同树时两次解析可降一次 | 保留每个安全时点、root 刷新、前台/几何与全部目标检查 |
| 3 | P04 模块完成到宿主消费的 400ms 轮询 | 直接位于每次工具返回路径，可能影响每步响应 | 先修明完成发布/清理顺序，再研究有界等待；不盲改 sleep |
| 4 | P05 物理截图编码与取消 | 完整 ARGB copy、缩放、JPEG、Base64 在主线程回调里执行 | 独立有界 executor、迟到回收；树和输入仍按原主线程顺序 |
| 5 | P06 后台 capture 直接生成最终缩放快照 | 可避免先克隆全尺寸，再立即缩放回收 | 独立快照、JPEG 锁外；先量 FRAME_LOCK 占用与新鲜度 |
| 6 | P07 明确无输入分支的固定 800ms | 审计挑战/特定目标拒绝仍等待，源码工作量明确 | 逐分支证明无输入；不动真实动作、首次收起、确认恢复和交接 |
| 7 | P08/P09 PageGuard 局部派生资源、后台 RPC 事件等待 | 有重复图像解码和每 RPC 20ms 轮询 | 保留各 ROI 独立检查、响应 token、取消与 teardown 语义 |
| 8 | P10 原生历史图片/请求体增长调查 | 若旧图反复上传，可能比微优化更重要；现状尚未确认 | 先实测图片数/字节/token，不先裁历史 |

**只想做一个低风险补丁：选 P01。想优先降低 Phone Use 本地成本：先测 P02/P05/P06。想改善每步感知延迟：先测 P04/P07。** 不同目标不能拿一个总墙钟数字混在一起比较。

- 不移除 UID、task/token、generation、锁屏、安全窗、密码、CAPTCHA、取消和超时；不并行动作或放宽执行互斥。
- 后台故障停止，不回退物理屏；仅既有明确应用冲突交接可按授权切换，旧观察立即作废。
